# UDP full cone NAT on a stock OpenWrt 25.12.5 router (no reflash)

## Rationale

The router (official OpenWrt 25.12.5 x86/64, kernel 6.12.94, firewall4, apk) masquerades LAN
traffic with endpoint-dependent filtering, which blocks inbound hole punching for games, P2P and
WebRTC. The ISP CGNAT in front of it measured NAT1 (RFC 5780, 3/3 runs), so making the router
layer full cone gives LAN hosts NAT1 end to end. Reflashing (e.g. ImmortalWrt) is out of scope.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | `xt_FULLCONENAT` from llccd/netfilter-full-cone-nat, used through `iptables-nft` in `table ip nat` | Kernel module chosen by the user over a pure nftables dynamic-map emulation |
| Source pin | `74c5e6f3c7` (dev branch) with ImmortalWrt's `PKG_MIRROR_HASH` | Same C source as dev head `4254b68014`, which only changes the upstream Makefile; our `src/Makefile` replaces that file, so the older pin keeps a verified download hash |
| Kernel build | Official 25.12.5 x86/64 SDK, sha256 checked; kmod must depend on exactly the router's `kernel=6.12.94~a7bc15f451f9652701ba04af9cfb0b95-r1` | The apk kernel pin is the only guard against a config-incompatible module; never bypassed (`--force-*`, `--no-depends`) |
| Conntrack events | `patches/100-no-ct-event-notifier.patch`: never register the conntrack event notifier on >= 5.15 without the ImmortalWrt `CHAIN_EVENTS` hack; log that once (`pr_info_once`) instead of the upstream "warning: failed to register" on every rule reload | 6.12 has one event callback per netns, owned by ctnetlink (e.g. nlbwmon, `conntrack -E`). If the module took it first, a later ctnetlink load would WARN and the module's unregister on a rule flush would clear ctnetlink's callback. Mappings are reclaimed lazily by `check_mapping()` instead |
| Inbound forwarding | `chain-pre/forward` rule `meta l4proto udp iifname @fullcone_wan ip daddr @fullcone_lan ct status dnat accept` | fw4 only emits `ct status dnat accept` in `forward_wan` when the zone has port forwards; without it the DNATed inbound UDP is dropped (found in the QEMU lab: mapping hit, still NAT3). A router that already has port forwards has that rule, but the package must not rely on it. Empty sets (disabled) make the rule inert |
| Scope | IPv4 UDP from the LAN subnet out of the WAN device. TCP, ICMP and IPv6 unchanged | Smallest behavior change; the fw4 `srcnat_wan` bypass rule and `FULLCONE_POST` both match UDP only, so TCP keeps fw4 masquerade |
| fw4 integration | `table-pre` sets `fullcone_lan` / `fullcone_wan` + `chain-pre/srcnat_wan` rule `meta l4proto udp oifname @fullcone_wan ip saddr @fullcone_lan return`; script include `/usr/share/fullcone/fullcone.sh` (`fw4_compatible 1`) | Sets are filled only after the FULLCONENAT rules load, so any failure leaves empty sets = stock masquerade |
| Rule order | Jumps to `FULLCONE_PRE` / `FULLCONE_POST` are appended | Jumps added earlier by other services (e.g. Docker) come first, so their published ports win over mappings |
| Excluded ports | `exclude_port` 41641 51820 9993 32448 21116 return early in `FULLCONE_PRE` | Common VPN / remote-access UDP services on the router itself keep inbound traffic even if a LAN mapping reuses the port |
| Config derivation | LAN from `network.lan` ipaddr/netmask, WAN `pppoe-wan` for PPPoE, else `network.wan.device`; overridable | fw4 starts (S19) before network (S20), so runtime state is not available |
| Config apply | `/etc/init.d/fullcone` has no process, only `procd_add_reload_trigger fullcone` → `firewall reload` | LuCI apply runs `reload_config`; the include re-applies on every fw4 start/reload |
| Packaging | `kmod-ipt-fullconenat`, `iptables-mod-fullconenat` (IPv4 only, depends on `libxtables`), `fullcone` (backend), `luci-app-fullcone` (Network → Full Cone NAT) | `luci-base` is an `EXTRA_DEPENDS` because the SDK has no luci feed |
| Rollout | Ships `enabled '0'`; `FULLCONE_FORCE=1 /usr/share/fullcone/fullcone.sh` for a soak that a reboot or firewall reload undoes; VM snapshot first | `kernel.panic_on_oops=1` means a module bug reboots the router |

Superseded finding: the earlier review said the module does not compile on 6.12. That review read
the stale `master` branch (2022); the dev branch already has the 5.15+ notifier API and a guard
against replacing an existing notifier. Only the guard was tightened (above).

## Impact

- LAN IPv4 UDP leaving `pppoe-wan` gets endpoint-independent mapping and filtering; inbound UDP to
  a mapped port is DNATed to the LAN host, except the excluded ports.
- UDP that a proxy client routes through its TUN does not get full cone (accepted).
- Mapping memory is not actively reclaimed: at most one small entry per LAN ip:port used for
  direct UDP; disabling unloads the module and frees it. New UDP flows take one global spinlock.
- Uninstall (`apk del luci-app-fullcone fullcone iptables-mod-fullconenat kmod-ipt-fullconenat`)
  flushes the sets first, removes the chains and the firewall include, reloads fw4, then deletes
  the two set objects (`fw4 reload` flushes the table but keeps sets). A modified
  `/etc/config/fullcone` stays behind, as apk does for any changed conffile.
- Each firmware upgrade changes the kernel pin: the feed needs an `sdk/<release>-<target>.env`
  for the new release (see `docs/plan/2026-11-01-feed.md`). Remove the four packages before an
  attended sysupgrade.
- `apk upgrade` keeps the four packages: the official 25.12.5 feeds have no packages with these
  names, `/etc/apk/world` pins each to the installed file's hash (`name><Q1...`), and the kernel
  stays pinned. A third-party feed that ships same-named packages could replace them; if an
  iptables upgrade ever broke `libipt_FULLCONENAT.so`, the include fails closed to stock masquerade.
  Checked 2026-10-29 on the router after `apk update`: `apk upgrade --simulate` changes nothing,
  `apk upgrade --available --simulate` reinstalls 60 same-version packages, none of them ours,
  kernel, kmods, iptables, libxtables or firewall4.

## TCP NAT1 for chosen LAN endpoints (2026-11-01)

### Rationale

Some uses (e.g. exposing a LAN service through the CGNAT mapping, TCP hole punching) need TCP
NAT1, but only for a few LAN `ip:port` endpoints chosen in LuCI, not for all TCP.

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | One stock fw4 port forward per endpoint (LuCI Network → Firewall → Port Forwards): protocol TCP, external port = internal port | `xt_FULLCONENAT` only maps UDP (`protonum != IPPROTO_UDP` at `xt_FULLCONENAT.c:453,922,1114`). fw4 masquerade already keeps the TCP source port, so mapping is endpoint independent; the forward adds endpoint-independent filtering. No package change |
| Semantics | Static: inbound is forwarded whether or not the LAN app has sent anything | A dynamic open-after-outbound design needs more code for little gain; the whitelist is chosen by the user |
| Whitelist UI | The existing Port Forwards page, not a list on the Full Cone NAT page | Same nft rules, plus validation and NAT loopback, with no code to maintain |

### Impact

- A forwarded port is reachable from the internet whenever a CGNAT mapping for `wan:P` exists
  (the LAN app keeps an outbound connection from `P`), even if nothing listens on the LAN host.
- Inference, not verified (needs a second subscriber line): other subscribers inside the ISP's
  100.64.0.0/10 space may reach `wan:P` directly with no mapping; every port forward has this.
- Endpoint-independent mapping relies on masquerade keeping the source port; on a tuple clash
  (another LAN host using `P` to the same remote endpoint) that one flow gets another port.
- Avoid ports already published by other services (e.g. Docker) and `fullcone.exclude_port`.

### Verification (real router, 2026-11-01)

- fw4 `srcnat_wan` is plain `masquerade` (no `random` / `fully-random`); 78/78 masqueraded LAN
  TCP flows kept their source port.
- One local port to three TCP STUN servers (Cloudflare, Nextcloud, stunprotocol.org) got the
  same CGNAT mapping, address and port: CGNAT TCP mapping is endpoint independent.
- End to end with a temporary forward `wan:40123 → <LAN host>:40123` (removed afterwards): a
  script on that host held a TCP STUN binding from port 40123 and listened on it. Conntrack showed the
  STUN flow leaving via the `pppoe-wan` address with port 40123 kept (not via the proxy TUN). A
  phone on cellular data, which had never been contacted, opened the STUN-mapped public
  address; the script logged both connections and router conntrack showed them DNATed to
  the LAN host's port 40123, `ASSURED`. The CGNAT forwards unsolicited inbound TCP: NAT1 for TCP.
- After cleanup: no leftover uci or nft rule, the existing forwards unchanged, UDP full cone
  still `mode fullcone`.
