# UDP full cone NAT on a stock OpenWrt 25.12.5 router (no reflash)

## Rationale

The router (official OpenWrt 25.12.5 x86/64, kernel 6.12.94, firewall4, apk) masquerades LAN
traffic with endpoint-dependent filtering, which blocks inbound hole punching for games, P2P and
WebRTC. The ISP CGNAT in front of it measured NAT1 (RFC 5780, 3/3 runs), so making the router
layer full cone gives LAN hosts NAT1 end to end. Reflashing (e.g. ImmortalWrt) is out of scope.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | `xt_FULLCONENAT` from llccd/netfilter-full-cone-nat, used through `iptables-nft` in `table ip nat` | Kernel module chosen by the user over a pure nftables dynamic-map emulation |
| Source pin | `74c5e6f3c7` (dev branch) with ImmortalWrt's `PKG_MIRROR_HASH` | Same C source as dev head `4254b68014`, which only changes the upstream Makefile; our `src/Makefile` replaces that file, so the older pin keeps a verified download hash |
| Kernel build | Official 25.12.5 x86/64 SDK, sha256 checked; kmod must depend on exactly the router's `kernel=6.12.94~a7bc15f451f9652701ba04af9cfb0b95-r1` | The apk kernel pin is the only guard against a config-incompatible module; never bypassed (`--force-*`, `--no-depends`) |
| Conntrack events | `patches/100-no-ct-event-notifier.patch`: never register the conntrack event notifier on >= 5.15 without the ImmortalWrt `CHAIN_EVENTS` hack; log that once (`pr_info_once`) instead of the upstream "warning: failed to register" on every rule reload | 6.12 has one event callback per netns, owned by ctnetlink (e.g. nlbwmon, `conntrack -E`). If the module took it first, a later ctnetlink load would WARN and the module's unregister on a rule flush would clear ctnetlink's callback. Mappings are reclaimed lazily by `check_mapping()` instead |
| Inbound forwarding | `chain-pre/forward` rule `meta l4proto udp iifname @fullcone_wan ip daddr @fullcone_lan ct status dnat accept` | fw4 only emits `ct status dnat accept` in `forward_wan` when the zone has port forwards; without it the DNATed inbound UDP is dropped (found in the QEMU lab: mapping hit, still NAT3). A router that already has port forwards has that rule, but the package must not rely on it. Empty sets (disabled) make the rule inert |
| Scope | IPv4 UDP from the LAN subnet out of the WAN device. TCP, ICMP and IPv6 unchanged (TCP and masqueraded IPv6 are optional since 2026-11-18, see the last two sections) | Smallest behavior change; the fw4 `srcnat_wan` bypass rule and `FULLCONE_POST` both match UDP only, so TCP keeps fw4 masquerade |
| fw4 integration | `table-pre` sets `fullcone_lan` / `fullcone_wan` + `chain-pre/srcnat_wan` rule `meta l4proto udp oifname @fullcone_wan ip saddr @fullcone_lan return`; script include `/usr/share/fullcone/fullcone.sh` (`fw4_compatible 1`) | Sets are filled only after the FULLCONENAT rules load, so any failure leaves empty sets = stock masquerade |
| Rule order | Jumps to `FULLCONE_PRE` / `FULLCONE_POST` are appended | Jumps added earlier by other services (e.g. Docker) come first, so their published ports win over mappings |
| Excluded ports | `exclude_port` 41641 51820 9993 32448 21116 return early in `FULLCONE_PRE` | Common VPN / remote-access UDP services on the router itself keep inbound traffic even if a LAN mapping reuses the port |
| Config derivation | LAN from `network.lan` ipaddr/netmask, WAN `pppoe-wan` for PPPoE, else `network.wan.device`; overridable | fw4 starts (S19) before network (S20), so runtime state is not available |
| Config apply | `/etc/init.d/fullcone` has no process, only `procd_add_reload_trigger fullcone` → `firewall reload` | LuCI apply (rpcd) raises `config.change` itself; the include re-applies on every fw4 start/reload. Shell changes use `/etc/init.d/fullcone reload`, not `reload_config` (see "Switching off" below) |
| Packaging | `kmod-ipt-fullconenat`, `iptables-mod-fullconenat` (IPv4 only, depends on `libxtables`), `fullcone` (backend), `luci-app-fullcone` (Network → Full Cone NAT) | `luci-base` is an `EXTRA_DEPENDS` because the SDK has no luci feed |
| Rollout | Ships `enabled '0'`; `FULLCONE_FORCE=1 /usr/share/fullcone/fullcone.sh` for a soak that a reboot or firewall reload undoes; VM snapshot first | `kernel.panic_on_oops=1` means a module bug reboots the router |

Superseded finding: the earlier review said the module does not compile on 6.12. That review read
the stale `master` branch (2022); the dev branch already has the 5.15+ notifier API and a guard
against replacing an existing notifier. Only the guard was tightened (above).

## Impact

- LAN IPv4 UDP leaving `pppoe-wan` gets endpoint-independent mapping and filtering; inbound UDP to
  a mapped port is DNATed to the LAN host, except the excluded ports.
- UDP that a proxy client routes through its TUN does not get full cone (accepted).
- Mapping memory is not actively reclaimed: at most one small entry per LAN ip:port used for
  direct UDP; disabling unloads the module and frees it. New UDP flows take one global spinlock.
- Uninstall (`apk del luci-app-fullcone fullcone iptables-mod-fullconenat kmod-ipt-fullconenat`)
  flushes the sets first, removes the chains and the firewall include, reloads fw4, then deletes
  the two set objects (`fw4 reload` flushes the table but keeps sets). A modified
  `/etc/config/fullcone` stays behind, as apk does for any changed conffile.
- Each firmware upgrade changes the kernel pin: the feed needs an `sdk/<release>-<target>.env`
  for the new release (see `docs/plan/2026-11-01-feed.md`). Remove the four packages before an
  attended sysupgrade.
- `apk upgrade` keeps the four packages: the official 25.12.5 feeds have no packages with these
  names, `/etc/apk/world` pins each to the installed file's hash (`name><Q1...`), and the kernel
  stays pinned. A third-party feed that ships same-named packages could replace them; if an
  iptables upgrade ever broke `libipt_FULLCONENAT.so`, the include fails closed to stock masquerade.
  Checked 2026-10-29 on the router after `apk update`: `apk upgrade --simulate` changes nothing,
  `apk upgrade --available --simulate` reinstalls 60 same-version packages, none of them ours,
  kernel, kmods, iptables, libxtables or firewall4.

## TCP NAT1 for chosen LAN endpoints (2026-11-01)

Superseded 2026-11-18 for the whole LAN by TCP in `xt_FULLCONENAT` (last section). Port forwards
stay the answer for a fixed endpoint that must be reachable with no outbound connection open; the
CGNAT measurements below still hold.

### Rationale

Some uses (e.g. exposing a LAN service through the CGNAT mapping, TCP hole punching) need TCP
NAT1, but only for a few LAN `ip:port` endpoints chosen in LuCI, not for all TCP.

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | One stock fw4 port forward per endpoint (LuCI Network → Firewall → Port Forwards): protocol TCP, external port = internal port | `xt_FULLCONENAT` only maps UDP (`protonum != IPPROTO_UDP` at `xt_FULLCONENAT.c:453,922,1114`). fw4 masquerade already keeps the TCP source port, so mapping is endpoint independent; the forward adds endpoint-independent filtering. No package change |
| Semantics | Static: inbound is forwarded whether or not the LAN app has sent anything | A dynamic open-after-outbound design needs more code for little gain; the whitelist is chosen by the user |
| Whitelist UI | The existing Port Forwards page, not a list on the Full Cone NAT page | Same nft rules, plus validation and NAT loopback, with no code to maintain |

### Impact

- A forwarded port is reachable from the internet whenever a CGNAT mapping for `wan:P` exists
  (the LAN app keeps an outbound connection from `P`), even if nothing listens on the LAN host.
- Inference, not verified (needs a second subscriber line): other subscribers inside the ISP's
  100.64.0.0/10 space may reach `wan:P` directly with no mapping; every port forward has this.
- Endpoint-independent mapping relies on masquerade keeping the source port; on a tuple clash
  (another LAN host using `P` to the same remote endpoint) that one flow gets another port.
- Avoid ports already published by other services (e.g. Docker) and `fullcone.exclude_port`.

### Verification (real router, 2026-11-01)

- fw4 `srcnat_wan` is plain `masquerade` (no `random` / `fully-random`); 78/78 masqueraded LAN
  TCP flows kept their source port.
- One local port to three TCP STUN servers (Cloudflare, Nextcloud, stunprotocol.org) got the
  same CGNAT mapping, address and port: CGNAT TCP mapping is endpoint independent.
- End to end with a temporary forward `wan:40123 → <LAN host>:40123` (removed afterwards): a
  script on that host held a TCP STUN binding from port 40123 and listened on it. Conntrack showed the
  STUN flow leaving via the `pppoe-wan` address with port 40123 kept (not via the proxy TUN). A
  phone on cellular data, which had never been contacted, opened the STUN-mapped public
  address; the script logged both connections and router conntrack showed them DNATed to
  the LAN host's port 40123, `ASSURED`. The CGNAT forwards unsolicited inbound TCP: NAT1 for TCP.
- After cleanup: no leftover uci or nft rule, the existing forwards unchanged, UDP full cone
  still `mode fullcone`.

## TCP in xt_FULLCONENAT, and crash hardening (2026-11-18)

### Rationale

Port forwards give TCP NAT1 only to endpoints chosen in advance. The user wants it for the whole
LAN subnet, behind a switch that ships off, and requires that no unexpected input can panic the
kernel: the router kernel has `CONFIG_PANIC_ON_OOPS=y` and OpenWrt sets `kernel.panic=3`, so any
oops in the module reboots the router. Anomalies must go to the kernel log instead.

Routers using the feed may also run OpenClash (`luci-app-openclash` 0.48.002 from this feed).
The analysis below covers its `redir-host-tun` mode with `china_ip_route` enabled, and fw4 with
`flow_offloading=1`.

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | `patches/210-tcp.patch`: the IPv4 target maps UDP and TCP; `struct nat_mapping` gets `proto` and every lookup (`get_mapping_by_ext_port` before `check_mapping()`, both `get_mapping_by_int_src*`, `find_appropriate_port`, `handle_dying_tuples`) matches it. The iptables rules decide which protocols reach the target | UDP-only was only three protocol guards; ports go through the `u.udp.port` union member, which aliases `u.tcp.port`. Without `proto` a UDP and a TCP mapping on the same ext port alias, and inbound TCP could be DNATed to the host that owns the UDP mapping |
| Switch | `option tcp '0'`. `fc_protos` returns `udp` or `udp tcp`; it drives both the FULLCONENAT rules and a new `fullcone_proto` set used by the two fw4 rules (`meta l4proto @fullcone_proto`) | One list, so fw4's masquerade bypass and the module rules cannot disagree. The set is filled after the rules, and any failure flushes it: stock masquerade |
| Excluded ports | `exclude_port` RETURN rules are added per protocol | Router services on those ports keep inbound TCP too |
| Hardening | `patches/200-hardening.patch`, separate from TCP so UDP users get it too: `ct == NULL` → `XT_CONTINUE` (both targets); `masq_index` only set with a known out device; `get_device_ip()` through `__in_dev_get_rcu()` / `rcu_dereference()`; checkentry rejects non-IPv4, non-`init_net`, `rangesize != 1`, an inverted `--to-source`, a `--to-ports` range starting at 0, and returns `nf_ct_netns_get()` errors | Each is an input that could oops or corrupt state; each now logs a ratelimited `xt_FULLCONENAT:` line and continues or refuses the rule. `--to-ports 0-65535` (accepted by `libipt_FULLCONENAT`) wrapped the old `uint16_t range_size` to 0, a division by zero with `--random`. `nf_ct_netns_get()` failures were ignored but `destroy` still put the reference. IPv6 rules can never load: `fullconenat_tg6()` has the old unbounded search and no `libip6t` is shipped |
| Port search | Original port first, then at most 128 probes from a random start; if all are taken, plain SNAT with the rule's own range and no mapping (`skip_mapping`, one unlock) | The old loop did up to 64512 lookups under the global spinlock in softirq and then freed a live mapping, moving inbound traffic of a live flow to another host. 128 is the nf_nat core bound |
| Not changed | Conntrack event notifier (still never registered), the global lock, lazy reclaim | Same as UDP. A WARN inside `nf_nat_setup_info()` logs only (`panic_on_warn` is 0), and our call pattern (one manip per direction, only while not initialized) does not reach it. Logging uses `pr_info_ratelimited` (`_printk_deferred` is not exported in 6.12.94) |
| Upgrade | `fullcone` post-upgrade (`PKG_UPGRADE=1`, verified in the SDK's `package-pack.mk`) runs `fullcone.sh stop` before `firewall reload` | apk replaces the `.ko` but the loaded module stays in use; without unloading, TCP rules would hit the old UDP-only module (plain SNAT, no mapping) until a reboot |
| Releases | `fullconenat` r4, `fullcone` r4, `luci-app-fullcone` r3 | `apk upgrade` needs a new release |

### Impact

- With `tcp=1`, while a LAN host has a TCP connection open from port `P` out of the WAN device,
  anyone can open a TCP connection to `wan:P` and reach that host. Only apps listening on their
  outgoing port use it; other hosts answer with a reset. Off by default.
- OpenClash: only LAN TCP that OpenClash returns early leaves `pppoe-wan` masqueraded and can
  get NAT1: destinations in `@china_ip_route`, destination ports outside `@common_ports` (only
  when `common_ports` is set; otherwise the set and rule do not exist), blacklisted LAN hosts.
  TCP that clash carries gets the proxy's or the router's mapping. Inbound DNATed flows do not
  touch OpenClash: `openclash_mangle` returns WAN-addressed packets (`ip daddr @localnetwork
  return`, the set holds `100.64.0.0/10` and the WAN IPs, init script lines 1404-1409) before
  `dstnat` runs, and the LAN host's replies via `ct direction reply return`. OpenClash's IPv4
  `dstnat` rules in this mode only match port 53.
- Flow offloading: the target only runs for the first packet of a new conntrack, before the flow
  is established and can be offloaded. fw4's `meta l4proto { tcp, udp } flow offload @ft` comes
  before the chain-prepend includes in `forward` (`ruleset.uc` lines 137-140), so inbound DNATed
  flows are offloaded too once established. Mapping liveness is a conntrack lookup, and offloaded
  flows keep their conntrack entry.
- Mapping memory grows with TCP connections: about one entry per external port and protocol
  (estimate: ~64k ports x ~128 bytes ≈ 8 MB per protocol at worst); disabling frees it.
- New TCP connections from the LAN take the global spinlock, as new UDP flows already did.

## IPv6 (NAT66) and the inbound flow list (2026-11-18)

### Rationale

Some routers masquerade IPv6 (fw4 `masq6` on the wan zone), typically when the ISP delegates no
prefix and the LAN uses ULA addresses. fw4's masquerade there behaves like IPv4 before fullcone:
port-preserving mapping, closed filtering (NAT3). The user wants full cone for that case too, behind
a switch that ships off. Routed IPv6 (a delegated prefix, no `masq6`) has no NAT and stays out of
scope: inbound IPv6 there is a firewall rule question. The user also wants the "Inbound UDP/TCP
flows to the LAN" counts in LuCI to expand into the flows themselves. The crash requirement from
the TCP section still applies. This section replaces that section's statements that IPv6 rules
can never load and that no `libip6t` is shipped.

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | `patches/220-ipv6.patch`: the IPv6 target (`fullconenat_tg6`, NAT66 masquerade) gets what 200 and 210 gave IPv4. That is `proto` in `struct nat_mapping6`, matched by every lookup; `find_appropriate_port6` with `u32` range math, at most 128 probes from a random start and plain SNAT without a mapping when all are taken; `newrange` zeroed | The upstream IPv6 path had the old IPv4 bugs: `uint16_t range_size` wraps to 0 for `--to-ports 0-65535` (division by zero with `--random`), an unbounded search under the spinlock, and a live mapping freed when no port was free. `nf_nat_range2` has `base_proto`, which the rule's `nf_nat_range` lacks and was left uninitialized |
| Rule check | `fullconenat_tg_check_common` holds the shared tail (`init_net`, `nf_ct_netns_get`, refcount). The IPv4 check keeps its range checks; the new `fullconenat_tg6_check` rejects an inverted `--to-source` (`ipv6_addr_cmp`) and a `--to-ports` range starting at 0 or inverted, each with its own log line ("... IPv6 ..."). The IPv4 family check is gone | Each family validates the layout it actually gets; the old shared check rejected IPv6 only because of the family test. Distinct log lines tell the families apart in `dmesg` |
| Userspace | `iptables-mod-fullconenat` also ships `libip6t_FULLCONENAT.so`; `fullcone.sh` runs `xtables-nft-multi ip6tables-nft` | `xtables-nft` (already pulled in by `iptables-nft`) is built with `libiptext6`; the `ip6tables-nft` package would only add symlinks and `kmod-ip6tables` |
| Switch | `option ipv6 '0'`, `option lan6_subnet ''` (default `network.globals.ula_prefix`). IPv6 rules go into `table ip6 nat` only when `ipv6=1`, some fw4 zone has `masq6=1` and a subnet is known; otherwise IPv6 is left to fw4 and the reason is logged (status `"ipv6":"inactive"`) | Without `masq6` there is no NAT66 to replace; adding NAT66 on our own would change routing behavior nobody asked for. The subnet is read from uci for the same boot-order reason as `fc_lan` |
| fw4 integration | New `fullcone_lan6` set. The `chain-pre/forward` and `chain-pre/srcnat_wan` snippets get a second rule with `ip6 daddr` / `ip6 saddr @fullcone_lan6` | Same pattern as IPv4; `srcnat_wan` includes come before fw4's `masq6` rule (fw4 b6e5157 `ruleset.uc`) |
| Script layout | `fc_chains add|del` and `fc_rules` take the iptables command, so both families share them; `fc_chains6_del` only touches `table ip6 nat` when it exists. Failure handling stays all-or-nothing | No copy of the IPv4 code; an IPv4-only router never gets an `ip6 nat` table |
| Flow list | `fc_status` also returns `flows` (proto, remote and port, WAN port, LAN host and port, conntrack timeout), at most 100 per protocol; `inbound_udp` / `inbound_tcp` count both families. WAN IPv6 addresses come from `/proc/net/if_inet6`, the same uncompressed form `/proc/net/nf_conntrack` prints (`%pI6`) | No conntrack tool needed; the cap keeps the 5 s poll small |
| LuCI | `IPv6 (NAT66)` flag and `LAN IPv6 subnet` (shown when IPv6 is set); an IPv6 status row. The inbound rows become native `<details>`: count in the summary, flow table inside. The open state lives in the view, so the 5 s refresh does not collapse a list; `ip6short()` compresses addresses for display | No extra widget or library; `dom.attr` skips `null` and binds function values as listeners (luci.js, openwrt-25.12) |
| Tests | The lab gains IPv6: pppd `+ipv6`, WAN `2001:db8:a::10`, "internet" `2001:db8:b::1`/`::2`, ULA LAN `fd00:1::/48` with `masq6`. `check_tcp.py` became `check_cone.py udp\|tcp 4\|6 PORT` (server port 3480, off the STUN ports) | One script for every protocol and family, all in-process via `setns` |
| Releases | `fullconenat` r5, `fullcone` r5, `luci-app-fullcone` r4 | `apk upgrade` needs a new release |

### Impact

- With `ipv6=1` on a `masq6` router, while a LAN host has a flow open from port `P` (UDP, or TCP
  with `tcp=1`), anyone can reach it at `[wan IPv6]:P`, as for IPv4. Off by default; routed IPv6
  is never touched.
- OpenClash with `ipv6_enable=1` proxies IPv6 like IPv4: only IPv6 that leaves `pppoe-wan`
  directly gets full cone.
- IPv6 mappings have their own table and lock (`fullconenat6_lock`); `handle_dying_tuples` keeps
  its lock order (6 → 4 → dying list), and `fullconenat_tg6` takes only the IPv6 lock.
- The status call reads `/proc/net/nf_conntrack` once per poll, as before; the JSON grows by at
  most 200 short objects.

## Panic review and bounded mapping checks (2026-11-18)

### Rationale

The user asked whether the module can still panic the router. The review covered:
- The whole patched source (pristine tarball plus 000-220, 1529 lines).
- The kernel config: `PANIC_ON_OOPS=y`, but no soft lockup, hard lockup or hung task detector;
  `LIST_HARDENED` without `BUG_ON_DATA_CORRUPTION`; no `NF_CONNTRACK_CHAIN_EVENTS`, so the event
  callback is unreachable; no `DYNAMIC_DEBUG`.
- The panic sysctls: `panic_on_warn`, `panic_on_rcu_stall` and `panic_on_oom` are 0 in the lab
  image and, user-reported, on the router.

No oops path was found. NULL conntrack, every division and modulo, use after free across
`check_mapping()`, lock pairing and order, allocation failures and rule input are all covered.

One cost problem was left. `check_mapping()` / `check_mapping6()` looked up every tuple of a
mapping on each call, and every new flow on a mapping makes one call under the global spinlock.
New inbound flows to a mapped port, which anyone can open, therefore cost O(n²) conntrack lookups.

Lab measurements on r5 (2 vCPUs, `nf_conntrack_max` 63488):
- 20000 new flows at 5000 pps: the router fell behind and tracked 11399-13483 of them (IPv6:
  13459).
- 60000 flows: conntrack stopped at 23369, softirq used 13.9 s, and new LAN UDP flows lost 5 of
  150 (2 s timeout), with a worst first packet of 1986 ms.
- No oops or WARN in any run (the taint value was only the out-of-tree flag).

That is a DoS, not a panic, but cheap to remove.

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Mechanism | `patches/230-bounded-check.patch`. Both checks take tuples from the tail (oldest): a dead one is freed and counted down, a live one is moved to the head, and the scan stops after `CHECK_MAPPING_LIVE_PROBES` (4) live ones or when every remaining tuple is live. The mapping is valid when a live tuple is found, otherwise it is killed, as before | Each tuple is freed once, so dead-tuple work is paid for by its insertion; live work per call is constant. Every pass frees a tuple or counts a live one (at most 4), so the loop always ends. Rotation revisits every tuple within `refer_count / 4` checks, so dead tuples stay bounded by the live ones (about 2x at worst); the old scan kept exactly the live ones |
| Not changed | The global lock, port probing (128 at most), `handle_dying_tuples()` (unreachable without chain events), killing only mappings without a live tuple | Not part of the cost; validity semantics stay the same |
| IPv4 `newrange` | Zeroed as a whole like the IPv6 one | `base_proto` was uninitialized (`INIT_STACK_NONE`). The kernel reads it only with `NF_NAT_RANGE_PROTO_OFFSET`, which our extension never sets, and then only picks another port: hygiene, not a crash |
| Releases | `fullconenat` r6, `fullcone` r6 (`luci-app-fullcone` stays r4) | The kmod alone would be replaced on disk while the old module stays loaded; the `fullcone` post-upgrade unloads it so the firewall reload loads r6 |
| Tests | `test/fullcone/flood.py 4\|6 COUNT PPS` opens one mapping and sends COUNT new flows to it. `check.sh` floods 20000 at 5000 pps per family and requires at least 19000 tracked. The suite setup now also resets `ipv6=0` | The assertion fails on r5 (above) and passes on r6. The setup reset makes the suite independent of earlier lab state (it failed when a manual test left `ipv6=1`) |

This supersedes the TCP section's "Not changed" note on lazy reclaim cost and its per-flow cost
under the lock: the lock stays, the per-flow work under it no longer grows with the mapping.

### Impact

- A flood to a mapped port now costs the module about what the same packets cost against an
  unmapped port. The flows are still tracked and forwarded, so the conntrack table fills as with
  any port forward (documented under Limits in `docs/fullcone.md`).
- Tuple lists may hold some dead entries until the rotation reaches them (memory about 2x the
  live flows of a mapping at worst, 64 bytes each).
- Users on r5 get the new module on `apk upgrade` without a reboot.

## Switching off: what takes effect (2026-11-18)

### Rationale

The user asked whether turning TCP or IPv6 off can fail to take effect. Two gaps were found in the
lab, neither in the module or `fullcone.sh`:

1. The documented shell command ended with `reload_config`. `/sbin/reload_config` sends
   `config.change` only for configs whose `uci show` checksum differs from
   `/var/run/config.md5`, and only `reload_config` writes that file (nothing else in `/etc`,
   `/lib`, `/sbin`, `/usr/sbin`, `/usr/libexec` or rpcd refers to it). LuCI's apply goes through
   rpcd, which raises the event without updating the file. So `reload_config` does nothing:
   - the first time after a boot (`/var/run` is tmpfs, the file does not exist yet);
   - when a shell change restores the values of its last run, e.g. TCP turned on in LuCI and
     then off in the shell.
   The uci value then says off while the rules stay on, until the next firewall reload.
2. Inbound flows already open when an option is switched off keep working: conntrack keeps their
   NAT, and fw4 reloads do not delete conntrack entries.

### Decisions

| Topic | Decision | Why |
|---|---|---|
| Shell command | Docs use `uci commit fullcone; /etc/init.d/fullcone reload` (its `reload_service` runs `firewall reload` directly). One sentence says why not `reload_config` | Applies every time, synchronously; LuCI is unaffected |
| Open flows | Documented in Limits (new inbound flows stop at once; open ones run until they close or idle out; a reboot ends them). Not flushed | `fullcone.sh` cannot tell full cone entries from port forward entries in conntrack (same DNAT shape), and deleting them needs the `conntrack` tool, which stock OpenWrt does not ship. fw4 itself leaves open flows alone on every rule change |
| Lab suite | Switches go through LuCI's rpcd calls (`test/fullcone/luci_set.sh`: login, `uci set`, `uci apply` with rollback, `uci confirm`) or the documented command. TCP off runs with `/var/run/config.md5` deleted, as after a boot. `reload_config` is no longer used | Tests what users run. The old `reload_config` steps also queued reloads for every config changed earlier, which once overlapped a NAT check |

### Impact

- Docs only for routers: no package change, no new release.
- Someone who switched TCP or IPv6 off with `reload_config` may still have it on. `fullcone.sh
  status` (`tcp`, `ipv6`) shows the real state; `/etc/init.d/fullcone reload` fixes it.

### Verification (2026-11-18)
